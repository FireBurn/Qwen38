# DFlash2 two-sequence full-block batching hypothesis

In the recorded two-slot runs, common/speculative.cpp submitted DFlash batches containing two five-token blocks, while the selector graph traces after listening showed two one-sequence graphs. The draft metadata has dflash.attention.causal=false. Source inspection shows llama_context::decode sets embd_all for non-causal attention; llama_kv_cache::init_batch then calls split_seq for non-unified KV streams, producing one sequence per ubatch. This is consistent with, but does not alone prove every detail of, the observed graph splitting. Baseline response differences correlate with whether the second slot launched before or after the first draft; causality is unproven.

Hypothesis: an equal-length multi-sequence graph could amortize draft weight reads and dispatches. The private candidate selects split_equal only for exactly two complete five-token blocks on a DFlash2 model, two adjacent sequence IDs with one ID per token, non-unified streams, enough ubatch capacity and no used tokens; other inputs retain existing splitting. Even that bounded change may affect attention masks, cache indexing, lattice alignment or numerical rounding. It is not qualified, and the original anchor candidate is independent.

Before GPU testing, inspect model graph and memory output contracts, create meaningful guard tests including malformed/interleaved/unequal batches and capacity boundaries, and compile baseline/candidate privately. If this survives review, use instrumented real-model tests of per-sequence logits, hidden state, lattices, cache and token behavior with phase-matched scheduling and a control repeated under identical batching; verify no cross-sequence attention and no new GPU errors. Only after correctness, compare end-to-end multi-request throughput and latency under matched load and independently confirm. The single-sequence workload cannot benefit from this two-sequence change. Keep the GPU hold in force until a separately reviewed bounded test is defined.
