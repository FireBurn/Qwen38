# Observed-server DFlash width discovery

Compare maximum draft width 5 against observed width 4 on the installed llama-server build and locally cached target/draft, with all other server flags, GPU selection and sampling settings matching the recorded server configuration. Use the same private one-dword-copy and disabled-transfer-queue overrides in all arms; the historical server environment was not captured. Allocate the observed 327680 context but test one short synthetic prompt, not a long populated context. Each of 24 fresh server processes performs the same warmup and one 512-token request with seed 1234 and ignore_eos, in six alternating ABBA/BAAB blocks. The fixed prompt, environment and sequence are declared in the runner. Do not retry, extend or pool data.

For the primary outcome compare generated tokens per second for width 5 vs 4. Per-request CPU busy, background build count and runnable-thread samples must be available; match blocks if arm means differ by at most 5 CPU percentage points, 2 build processes and max(4,15% of pair mean) runnable threads. GPU busy/VRAM samples are optional and EBUSY is timestamped; do not count a startup GPU sensor gap as a missing CPU sample. Require each run to return 512 generated tokens, nonempty choices, positive draft counts and DFlash activation marker, and report observed acceptance and output hashes. Monitoring faults, competing GPU work, unexpected process exit or missing mandatory request-phase telemetry stops the batch. Capture device-wide VRAM, not per-process allocation. Positive lower 95% descriptive interval over at least four matched blocks is discovery evidence only and triggers separate confirmation and stochastic correctness/quality evaluation, not a configuration change. Different draft widths can produce different seeded outputs and acceptance; speed results alone do not prove distributional equivalence. No change to the user's server or settings.

Use the byte-verified private snapshot of the 0.8.0-dev executable and its llama.cpp libraries. LD_LIBRARY_PATH points to the snapshot; every child must map the expected private libraries, and hashes and identities are checked throughout. The system driver and libc remain shared and are pinned; the ongoing llama.cpp package build may change CPU load but cannot replace the private snapshot. This tests the old stack, not the future 0.9.0 installation.
