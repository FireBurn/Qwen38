# Single-sequence anchor-selector speed feasibility

The prior short real-server captures matched full lattices and outputs for the private single-sequence anchor-selector candidate at draft widths 3 and 4, including one 905-token populated prompt. More correctness work (additional seeds, long contexts, adversarial ties and general deployment) remains. Run this limited, non-adoption feasibility study now to determine whether the candidate is worth that further effort; a positive result is not correctness qualification or a production recommendation.

Use 16 fresh installed-server processes in four alternating ABBA/BAAB blocks, with the same reconstructed private baseline/candidate libllama, private baseline Vulkan backend and common ggml libraries, observed DFlash width 4, ngram-mod, Q8 KV, Flash Attention and sampler parameters. Per process warm up 16 tokens then generate 512 tokens from one fixed short seeded prompt. Audit hooks are disabled. Verify actual loaded library paths, hashes/stat identities, generated token counts, response hashes and draft/accept counters. Use phase-tagged CPU busy/build-count/runqueue telemetry and no competing inference. Block match: arm means within 5 percentage points CPU busy, 2 build processes, and max(4,15% of mean) runnable threads. A positive lower bound of a descriptive t interval on at least four matched blocks is a discovery signal only; require independent confirmation and broader correctness before any adoption. Stop on output mismatch, new GPU error, competing inference, mapping/identity failure, timeout or missing required telemetry; no retry. One-dword copy and disabled transfer queue are process-local safety overrides. Preserve the GPU hold for other work.
