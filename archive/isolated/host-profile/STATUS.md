# CPU work during GLU fusion

Evidence: runs/20261023T195017Z/summary.json and results.json. Four symmetric off/fused/fused/off runs use the same immutable GLU host and shader, with 128 generated tokens and two repetitions. The private benchmark implementation enables perf counters only inside the original timed decode regions. Actual loaded libraries are checked. control-check/proof.json verifies that the FIFO gate excludes CPU work outside those regions.

Mean user CPU time per token: off 12.1278 ms, fused 11.7324 ms (-3.26%). Mean user instructions: off 24.7220 million, fused 25.3624 million (+2.59%). User cycles fell 2.73%. Counters ran without multiplexing. Background compilation remained active.

The instruction increase is evidence of additional aggregate user work. It is not attribution to the fusion pass alone: these counters include driver and CPU backend threads and effects of GPU waiting. Aggregate CPU time is not serial host latency, and must not be added to GPU timestamp durations. In particular, these results do not establish that extra CPU time cancelled the focused GPU saving. No quiet token throughput claim follows.

Source audit found seven fusion passes called consecutively in vk_mega_flush. Several independently search the operation registry and traverse records; the gather pass compacts records even without a successful fusion, while GLU compacts only after a match. Potential next work is measuring individual pass costs and avoiding unnecessary scans/copies while preserving pass order and exact record semantics. This is a hypothesis requiring attribution and controlled comparison, not a demonstrated bottleneck. Existing shader-only optimizations remain independently useful candidates.

CPU-only follow-up: measure_glu_rewrite.py compiles the actual immutable GLU fusion function and replays one historical pair, repeated zero/one/56 times, with synthetic registries of two/128 entries. Seven trials of 10,000 calls use thread CPU time, with clock reads outside each batch. Record/map restoration is included, so this is not isolated function attribution. Every rewritten record count is asserted. Median costs for two registry entries were 3.328/4.641/6.645 microseconds; for 128 entries, 4.145/5.963/8.036 microseconds. See glu-rewrite-cost.json, which pins the tested fusion source hash. Background compilation remained active. These synthetic shapes are not captured full model segments and reused descriptors are not a runnable GPU graph. The measurements lower the priority of optimizing this pass alone; they do not establish total production host rewrite cost or a token speed prediction. No runtime artifact or queued benchmark was changed.
