# Follow-up research and current hypotheses

Primary sources checked 2026-10-26. No package, driver, or production changes.

- https://github.com/ggml-org/llama.cpp/discussions/22663 reports Q3_K inefficiency on gfx1201 HIP, with gfx1200 Vulkan comparisons in a reply. This is a lead, not proof for our ACO shader. Our Q3 bias/row experiments already exist; first compare isolated instruction and matrix wall costs before repeating them.
- https://github.com/ggml-org/llama.cpp/pull/25483 is merged (Sep 17): skip unused MoE coopmat1 work. Our current dense C1/C2 quantized matvec diagnostic does not enter that expert matmul path. Relevant for future MoE variants, not a fix to the observed dense mega gap.
- https://github.com/ggml-org/llama.cpp/issues/25356 describes an MoE batch threshold cliff at 9 tokens on gfx1151. Current dense C1/C2 cases do not cross it. Do not import broad threshold changes without matching workload evidence.
- https://github.com/ggml-org/llama.cpp/issues/20846 reports scalar F16/BF16 loads on gfx900. Quantized hot kernels here differ, and existing two-column BF16 paths need inspection before any source rewrite. The report is not an established gfx1201 result.
- https://www.llvm.org/docs/CommandGuide/llvm-calc-occupancy.html documents a tool sharing LLVM occupancy math, including wave size and dynamic VGPR constraints. Installed LLVM23 lacks this executable. No installation attempted. It could cross-check static capacity, but occupancy is not performance or a complete persistent-kernel forward-progress proof.
- https://x.com/SemiAnalysis_/status/2113992350489788573 still returns 403. Its content remains unverified and has not been used to justify changes.

Current kernel hypotheses to discriminate after matched stream data:

1. Quantized virtual jobs use per-wave atomic reservations, usually chunk1 below4096 jobs. Larger chunks can reduce contention but waste tails; static assignment was already slower. Any follow-up should measure adaptive dynamic reservations with balanced tails, not repeat rejected static assignment.
2. The single prealloc_y last-tensor quantization cache introduces input-order sensitivity. Independent versus chain graphs are different workloads; sync-call counts alone cannot isolate synchronization cost.
3. 72-register policy changes matrix throughput only modestly in the first forward comparison. This is preliminary: complete repeats and chain cases before claiming register occupancy explains or fails to explain the gap.
4. Native can launch far more virtual matvec groups than a persistent grid. Persistent grid occupancy, scheduler issue traffic, and memory-level parallelism need separate controls. A theoretical occupancy increase does not guarantee enough outstanding loads or better bandwidth.

Matched-backend source audit: actual q8-two-column-f32/ggml-vulkan.cpp (10703 onward) selects MMVQ for Q3/Q4/Q5 at K5120/17408 for C1 and C2. Q6_K bypasses MMVQ on AMD in both cases. The Q8_0 C2 selector flag does not alter these four families. Keep this mixed arithmetic family distinction when interpreting aggregate nominal bandwidth. The source used by the benchmark is the private q8 backend, not a newly built upstream backend.

## Additional primary research

Fleet, AMD Research (2026): https://arxiv.org/html/2604.15379v1

The MI350 study coordinates persistent workers around cache locality and scoped dependencies, and explicitly discusses the occupancy cost of combining task types. Its chiplet scheduling and CDNA cache bits are not direct R9700 Vulkan replacements. Transferable experiment: evaluate task acquisition order and intermediate residency with an explicit working-set budget. Our dynamic-claim experiment tests acquisition overhead only; it does not implement Fleet. Avoid copying its cache policy: our earlier weight-streaming hint already has separate negative evidence. Fleet's occupancy discussion motivates resource measurement, not an assumption that dynamic register allocation is enabled for our wave64 pipeline.

Event Tensor Compiler (2026): https://arxiv.org/html/2604.13327v1

This work models dependencies between tiles rather than imposing an operator-wide sequence. Its runtime can enqueue consumers after producer dispatch, but still waits for actual dependencies before execution. Transferable longer-term design: independent matrix records may share a ready-task phase, while downstream reductions and aliases retain explicit completion edges. This is more extensive than changing task-claim size. Our old host submission coalescing retained all global barriers and did not test this design. A future implementation requires read/write-range dependency verification and bounded resident workers; removing barriers without those proofs is not equivalent to the paper's scheduler.

## ACO function-call / code-size lead

Official documentation: https://docs.mesa3d.org/drivers/amd/function-calls.html . ACO has a real call ABI (including indirect calls and caller/callee register preservation), primarily used by ray tracing. Calls may spill arguments/live registers to a VRAM stack; they do not imply per-task dynamic VGPR allocation.

Local source evidence: mtp-sched-keep-occupancy/source/src/amd/vulkan/radv_shader.c:576 inlines ordinary SPIR-V functions, removes unused implementations, and later inlines cooperative-matrix helpers again around622. radv_pipeline_rt.c invokes radv_nir_lower_call_abi at479 and1078. Simply adding a DontInline hint is therefore not an established compute-call implementation. No private Mesa change made.

Code-size comparison from existing resource diagnostics: native Q3 pipeline instances20328/12944bytes, Q3-only interpreted partition61184bytes, full combined approximately497KiB. Different specialization/reachability makes this an imperfect comparison. Static size alone does not prove instruction-cache misses: only executed paths matter. An outlining experiment would need explicit ABI lowering, argument/liveness and stack audit, resource qualification, bit-exact micro/model tests and matched performance. Treat as a compiler research lead, not a ready optimization.
