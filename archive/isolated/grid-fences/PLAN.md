# Directional grid fence experiment

Reference gridbar performs all-invocation device Buffer AcquireRelease, workgroup control barrier, leader device Buffer AcquireRelease atomicAdd and Acquire polling, workgroup control barrier, then all-invocation device Buffer AcquireRelease. Keep arrival counter, scopes, leader atomics, polling, both workgroup barriers, and all scheduling unchanged.

Hypothesis: entry needs Release to order completed accesses before arrival, while exit needs Acquire to order subsequent accesses after observing all arrivals. Entry Acquire and exit Release may be redundant. First test exit Acquire only, then entry Release plus exit Acquire, as separate derivatives of BF16-pair, not P variants. No relaxed atomic or workgroup-only substitution.

Required memory argument: every invocation releases earlier buffer writes before its group's leader increments; the workgroup execution barriers preserve the sequence. Leaders' acq_rel RMWs form the arrival chain; an Acquire load observing count>=target acquires every group in the generation. Other invocations pass the second WG barrier then their own device Acquire before consuming data. Next-generation arrivals cannot let the old generation complete early: all target increments must already have occurred. No data is written between the first release and exit except the leader counter, whose RMW retains release. Confirm formal Vulkan fence/control-barrier synchronization and actual SPIR-V memory semantics before promotion; numerical checks alone are insufficient proof.

## Formal-review correction before execution

Do NOT run build.py candidates yet. The argument above is incomplete: Vulkan program-order is within one invocation, and the release-before-WG-control / leader-atomic-after-control handoff needs a Buffer-class acquire on the other side of that control barrier. The ordinary GLSL barrier() must be inspected for its storage-class semantics. Similarly, acquiring a counter in the leader and broadcasting completion through an ordinary shared-only control barrier needs the Buffer-class synchronization chain audited. A passing output check does not establish these edges. The original barrier's stronger directional bits alone do not prove this handoff either; this is an audit finding, not a demonstrated runtime fault.

Safer next candidate to reason about: two explicit Workgroup-execution, Device-memory control barriers with Buffer|Shared AcquireRelease semantics around unchanged leader counter protocol. These give each participating invocation a release/acquire barrier with Buffer storage class on the appropriate side of the execution barrier. Confirm GLSL/SPIR-V validity, memory-model scopes and actual compiler lowering before GPU testing. Alternative add leader Buffer acquire fence after first control barrier and Buffer release fence before second, then all-invocation release/exit-acquire fences. Neither is implemented/adopted. Do not claim barrier removal or correctness proof for the earlier directional proposal.
