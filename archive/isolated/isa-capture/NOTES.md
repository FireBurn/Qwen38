# Private installed-driver representation capture

prepare.py derives bf16-pair host, build.py uses captured native libc++ compile/link commands in own bin; no installed or Claude tree changes. GGML_VK_MEGA_IR_DIR opt-in sets CaptureInternalRepresentationsKHR only when pipeline name contains megakernel and executable properties are supported. Three Vulkan API queries get representation count, byte sizes and data. Capture directory must exist. All other pipelines/calls retain original flags. No timing data uses this diagnostic host.

First compile failed due missing fstream include; fixed in generator. Re-running generator now tolerates pre-existing dangling symlinks. Build succeeds with existing warnings. Both reference/explicit9-frame checks match oracle, results.json. Capture64groups; ordinary performance tests use uninstrumented bf16-pair host192groups.

Current driver returns NIR Shader(s), ACO IR, Assembly. The Assembly representation begins: Shader disassembly is not supported ... LLVM not available, falling back to print_program. Therefore representation2 is the allocated/lowered hardware-instruction listing, NOT encoded machine-byte disassembly. Do not claim bytecode identity from text hashes. Its text is byte-identical for reference and explicit-grid-barrier candidates; NIR/ACO IR differ. comparison.json hashes all three. Current driver SHA and artifact identity remain those in prior manifests.

reference-opcode-counts.json counts textual mnemonic occurrences, NOT dynamic executed operations, latency, FLOPs or per-token counts. Listing contains packed integer dot and WMMA; therefore these instructions are already generated, not an untapped ISA feature by themselves. Next useful analysis is mapping peak live VGPR regions and repeated waits/loads to operator branches before proposing another resource rewrite. This tool makes that analysis use the installed compiler rather than assumptions from a possibly different local Mesa checkout.
