# GFX12 expert scheduling mode 2 audit

Primary LLVM PR170319 merged2026-01-09, commit475f022cb74cdf3b11c8211ead63122ef8b8c607. Metadata and file patches archived beside this note. Sources: https://github.com/llvm/llvm-project/pull/170319 and https://llvm.org/docs/AMDGPUUsage.html . The mode enables compiler-managed VMEM/VALU hazard waits, not a numerical approximation. It requires matching dependency tracking and HW_REG_WAVE_SCHED_MODE handling; changing the hardware mode without the compiler hazard implementation is invalid.

Installed LLVM23.1.3 accepts the option for gfx1201 wave64. Offline volatile load/multiply/store witness compiles in both modes. Mode1 adds one scheduling-mode write and two s_wait_alu sites; both retain two used VGPRs/six SGPRs and the same load/store counts. This proves local compiler support and a different hazard protocol, not correctness on hardware or a speedup. No GPU job or driver change was made for this audit.

Private pinned Mesa ACO source has no expert-scheduling/ESM2 support identified in its compiler/common source search. The actual mega path uses RADV/ACO; changing an LLVM codegen flag while building that driver does not apply this pass to its shaders. A meaningful experiment needs a complete ACO implementation of dependency tracking plus mode management, or an independently validated LLVM shader path. The small witness increases explicit waits, so there is no static instruction-count reason to prioritize a broad driver port ahead of the existing measured Q3 lead. Hardware scoreboard throughput could still differ; no stall-counter evidence or negative performance conclusion exists.
