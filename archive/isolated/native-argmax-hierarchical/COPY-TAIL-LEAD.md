# Candidate readback-copy tail mechanism

The captured stock backtrace surfaced device loss in `ggml_vk_buffer_read_2d`. In the preserved aa8 buffer implementation, discrete-device readback normally creates a temporary transfer context and records a buffer copy into a pinned or staging buffer. The test reads 4, 8 or 20 bytes for its 1, 2 or 5 output rows. The failing command, actual virtual source range, queue, allocation layout, memory residency and copy shader were not captured; the stack alone does not establish which GPU command faulted.

In the pinned private RADV source, the buffer-meta option 2 selects a two-dword compute-copy width, and the non-sparse raw-address NIR source builds a full-width input load before restricting stores for a partial last thread. An aligned 20-byte copy, for example, has three 8-byte source-load lanes under the simple modeled geometry: the last loads bytes 16–23 even though only bytes 16–19 are requested. If the requested 20 bytes end exactly at a mapped-page boundary and the following page is unmapped, that last load could cross into the unmapped page. The CPU arithmetic example enumerates 4-byte-aligned positions for 4-, 8- and 20-byte copies under explicitly stated alignment assumptions. This is a source-level risk hypothesis, not an assertion that the compiled ISA performs this access, that the next page was unmapped, or that it caused the observed fault. Buffer allocation padding could keep the load within a mapped page; the real GPU address and dispatch are unknown. The faulted address was page-aligned, which is compatible with multiple mechanisms and does not prove this one.

A future controlled diagnostic would need recorded per-case progress, source/destination device addresses and mapped allocation extents, effective queue/copy selection, disassembled actual meta shader, and isolation of readback from argmax execution. Any deliberate unmapped-page crossing risks another GPU reset and must not be run on the user's active GPU as an exploratory test. The current private GPU hold remains active; no GPU work was performed for this source audit.

## Allocation-padding qualification

The pinned `ggml_backend_buft_alloc_buffer_n_plan` pads each tensor's requested size to its backend alignment. The Vulkan backend reports `minStorageBufferOffsetAlignment` as that alignment and reports the tensor's logical byte size as its allocation size before the plan pads it. Under the modeled conditions of an at-least-8-byte power-of-two alignment, aligned tensor start and destination, and a mapped Vulkan buffer covering the planned padded size, the 2DW load for each 4-, 8- or 20-byte output fits within the padded tensor allocation. The accompanying CPU arithmetic model checks these cases for several alignments; with alignment 4, the modeled 4- and 20-byte cases would not have sufficient tensor padding. Therefore the preceding page-crossing scenario is not established for this actual test and may be inapplicable. Device limits, actual offsets, mapped extent and generated ISA were not logged. This does not exclude a different copy, alignment or synchronization failure.

The allocation-plan source is `ggml/src/ggml-backend.cpp` and the Vulkan buffer alignment/allocation-size functions are in the pinned backend host source; the faulting stack and conditional reconstruction remain as previously recorded. No GPU run was made for this qualification.
