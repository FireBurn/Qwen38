# Stock-control fault review

The failed expanded test was the first arm, with the unmodified aa8 stock Vulkan backend and the private copy2 driver verified through process mappings. Its candidate directory and hierarchical shader environment variables were only set for the later candidate arm. The GPUVM page fault and ring timeout were attributed by the kernel to the stock `boundary-check` process; the ring reset reported success. The userspace stack shows device loss surfaced during tensor readback, but asynchronous GPU execution means that does not identify the faulting dispatch or root cause.

The expanded source differs from the earlier passing checker only in six added dimensions and its reported totals. The output file contains 579 complete records, last complete `(k=1025, rows=5, pattern=4)`, plus a partial header. Writes were buffered and no per-case execution marker was recorded, so this does not establish which case was executing or even whether one of the added dimensions had been reached. Neither a specific shape nor the candidate shader can be identified as the cause from these records. The earlier test did execute the candidate in another process; this evidence alone cannot exclude a persistent effect or prove one.

The earlier known 4-DWORD copy issue is a separate observed failure, not an established explanation here; this run used the 2-DWORD copy setting. The candidate batch never started, so the boundary attempt supplies no candidate correctness comparison. The previous 630-case four-arm check is retained as a narrower result. No model or speed claim follows.

A local GPU-fault hold now stops the private batch wrapper before launching a GPU task; the expanded runner remains separately quarantined. No GPU test was run during this review. Any future diagnostic must first identify a safe environment, preserve exact per-case progress without buffered ambiguity, use bounded workloads and treat a recurrence as a stop condition; it must not pool this failed attempt with a successful run. The private backend remains experimental. In particular, its size arithmetic and multi-context resource ownership need review for extreme shapes and device lifetime independently of this fault.

## Offline follow-up

The inspected native scratch allocator submits and waits before resizing, and the prototype uses the existing split-K synchronization flag plus an explicit inter-dispatch shader-read/write barrier. This supports the intended ordering in the inspected single-context code; it is not a multi-context lifetime proof. A separate proposed bounds patch avoids relying on wrapping multiplication and prevents 32-bit shader chunk-end wrap. A Python arithmetic model passed 100,010 checks, but the patch is not compiled or GPU tested and is not a diagnosis of the stock fault.

A separate one-case `boundary-probe` prints and flushes a begin/pass marker and accepts only a listed shape, row count and pattern. Its `--list` mode was compiled and checked for 882 unique cases without initializing the GPU. It has not been run on the GPU, is not added to the guard allowlist, and the GPU-fault hold remains in place.

The archived 27 October `operator_bench` fault also reported `GCVM_L2_PROTECTION_FAULT_STATUS=0x00601030`, TCP client 0x8 and permission-fault value 3. The prior investigation correlated it with a default-copy negative reproduction; the current stock test explicitly set copy2. This is a matching hardware fault signature, not proof of a shared cause or of a copy-path failure. See `isolated/q3-pad112/diagnostics-attempt1-timeout/attempt.json` (its old fault lines are explicitly marked historical) and `isolated/native-swiglu-q8/driver-audit-20261028.json` for the prior attribution limits.

The bounds patch has now been compiled in a separate private host. The new binary has not run on the GPU and has no operator, model or performance qualification; the previously tested host and evidence are unchanged. The GPU-fault hold remains active.
