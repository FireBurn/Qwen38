# Research useful to this Vulkan Qwen effort

Sources checked 2026-10-21. These are design references, not measured speedups on the R9700. Most available implementations target CUDA; do not install them into the production environment.

| Project / primary source | Relevant mechanism | Application here | Limitation |

| [Mirage MPK](https://github.com/mirage-project/mirage) and [paper](https://arxiv.org/abs/2512.22219) | Compile model graphs into persistent tasks with a scheduler/runtime | Derive dependencies and a fixed schedule from tensor regions, instead of preserving original dispatch boundaries | CUDA-focused; the compiler/runtime is not a Vulkan drop-in |

## Further concrete experiments

1. **LDS liveness packing:** allocate one arena per element type, assign nonoverlapping offsets only to arrays reachable within the same operation, and reuse arena space across operations after a workgroup barrier. This directly lowers the combined FA/matvec shared allocation without changing mathematical operations. Implemented experimentally in isolated/pack_shared.py.
2. **Use a small number of graph templates:** decode n=1, speculative verification n=2/4/8, plus KV split-count buckets. Precompute schedules and descriptor topology; patch changing positions, lengths and addresses. This avoids treating the whole graph as a freshly uploaded general-purpose tape each time.
3. **Reduce intermediate materialization:** fuse norm+scale, sigmoid into GDN, and eventually producer epilogues with quantization or gating. On-the-fly quantization inside every row worker duplicates work; compare it against once-per-vector preparation rather than assuming fusion wins.
4. **Attention reduction ownership:** dedicate a head owner to combine chunk outputs. Fuse gating and compatible packing into that owner's epilogue. Avoid all-grid synchronization when only a head's chunks are dependencies.
5. **Grouped gate/up tasks:** schedule paired row tiles from separate weight matrices to compute SwiGLU locally. Mixed GGUF quant types need dispatch inside the task or separate specialised paired variants.
6. **End-to-end token handoff:** when an API request needs only the next token, investigate GPU argmax/top-k and compact transfer after the full LM-head computation. Preserve logits paths for scoring, logprobs and speculative acceptance; do not silently prune vocabulary.
7. **Adaptive draft length:** use measured acceptance and context-dependent verification cost to select DFlash length. Evaluate time per accepted token, including drafter and recurrent-state rollback, not just target decode throughput.
8. **Phase-specific scheduling:** persistent decode and normal prefill can be optimal together. A one-kernel target is useful only if its shared-memory/register footprint and scheduling actually reduce time.

Sparse attention, KV eviction, reduced weight precision and changes to the recurrence alter numerical/model behaviour. They are separate quality experiments, not correctness-preserving kernel optimisations.

## Additional findings from local measurements

- **Weight traffic estimate:** the captured decode touches 497 unique matvec descriptors totaling 15,692,349,440 bytes. See `weight_stream.py` / `weight-stream.json`. This is a descriptor-coverage estimate, not a DRAM counter measurement. It excludes non-matvec traffic. Using the whole GGUF size as bytes read per token overstates this workload's bandwidth use, because the file includes tensors not used by ordinary target decode.
- **Register pressure remains material:** the corrected full 256-thread shader uses 192 VGPRs and spills 30 SGPRs into VGPRs; it has no reported VGPR-to-memory spills. Merging shaders removes launches but imposes a larger common resource allocation on every operation. Keep tile-level scheduling and reduced live state as priorities.
- **Exact int4 x int8 via two dot8 operations:** native HIP arithmetic validation passes 1,048,576 rows. VGPR count falls from 36 to 13 in the synthetic kernel; measured memory-bound speed is essentially unchanged. See `isolated/isa/README.md`. Activation packing and Vulkan compiler exposure remain work before this can benefit real Q4_K kernels.
- **Recurrent-state copies:** an existing local patch already writes GDN snapshots directly into the recurrent cache (`llama-deep/patches-vk/0001-vulkan-write-gated-delta-net-state-snapshots-straigh.patch`). Its author reported a small gain on another local snapshot. The captured Claude graph still contains those copies; porting it would need current-layout alias checks and speculative rollback tests. Avoid claiming this as a newly discovered optimization.

## Kernel / AMDGPU submission direction

[Kernel user-mode queue documentation](https://docs.kernel.org/gpu/amdgpu/userq.html) and [MES documentation](https://docs.kernel.org/gpu/amdgpu/gc/mes.html) describe applications submitting queue packets through mapped queues and doorbells without a command-submission ioctl for every batch. This can reduce CPU submission overhead and is relevant to a busy CPU or GPU-driven task graph. It does not reduce the arithmetic or memory traffic inside a shader.

On this system `amdgpu.user_queue` is `-1` (automatic). The inspected Mesa snapshot has `AMD_USERQ` handling in common GPU information and a user-queue implementation in the Gallium AMDGPU winsys; the RADV winsys has no matching implementation in the inspected source. This is not evidence that merely setting that environment variable accelerates Vulkan. No queue/module parameter has been changed, and no speedup is claimed. A RADV implementation and hardware-specific validation would be required before benchmarking that route here.

## Reusable GPU command streams

The installed RADV advertises `VK_EXT_device_generated_commands`, including `deviceGeneratedCommands` and `dynamicGeneratedPipelineLayout`. This is a concrete alternative worth probing for CPU-side recording overhead. The [Khronos extension proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_device_generated_commands.html) allows GPU-selected compute pipelines and push constants through execution sets with compatible layouts.

A possible design is a cached command buffer containing per-operation generated-command executions and the existing dependency barriers, with only the indirect parameter stream patched for position, depth and buffer addresses. This preserves individual kernels' resource allocations. It is not a drop-in GPU graph: [compute command layouts](https://docs.vulkan.org/spec/latest/chapters/device_generated_commands/generatedcommands.html) do not include arbitrary barrier tokens, so dependent model operations cannot simply be packed into unsynchronized dispatch sequences. Preprocessing also costs GPU work. A microbenchmark must compare native cached dispatches, generated commands and the persistent tape before committing to an integration.

The single-submit experiment reinforces why caching matters: eliminating 19 host submission cuts produced one correct dispatch but reduced throughput. CPU recording had overlapped GPU execution; a monolithic launch serialized more of that preparation. This is an inference from host structure and GPU/whole-token timing, not a full timeline trace.

## Follow-up: compiled tile dependencies, 2026-10-21

[Event Tensor (MLSys 2026)](https://arxiv.org/html/2604.13327v1) compiles tiled producer/consumer events into integer counters and wait/notify operations. It offers static and dynamic scheduling, and describes advancing queue pushes before producer completion while preserving a wait before consumer execution. This separates scheduling latency from dependency completion. Its examples include independent Q/K attention work and MLP pipelining. These are NVIDIA results, not R9700 speed evidence.

**Transfer hypothesis:** Our range audit rejects removing almost all whole-operator barriers, but it does not rule out tile-level readiness. A concrete next audit should map an MLP gate/up tile to its activation and Q8 consumer, including the actual buffer reuse lifetime. A consumer waiting on a partial producer set must not occupy all persistent workers; producer progress and residency need explicit proof. Compiler-generated local schedules may avoid a generic per-op tape interpreter, but code growth and instruction-cache pressure need measurement. The current guided per-op queues do not provide this inter-op overlap.

[Ada-MK (2026)](https://arxiv.org/html/2605.11581v1) describes shared-memory page reuse, static execution-path generation, address permutation and moving dequantization into idle loader roles on Ada. Its reported gains are not transferable measurements. Our FA phase reuse independently validates that scratch lifetime modeling can change R9700 register allocation. Static instruction schedules and cache-load timing remain separate experiments; our post-arrival weight prefetch shows no established gain.

**Transfer hypothesis:** Specialize repeated layer/segment operator patterns instead of emitting an entire model's unrolled tape. This could remove opcode interpretation and repeated entry work without thousands of duplicated operator bodies. Retain runtime offsets/shape guards and exact fallback. Measure compile time, code size, VGPR/LDS, and full logits before throughput. Do not resurrect Claude's failed LDS tape staging without auditing its barriers and scratch ownership.

[llama.cpp issue 25618](https://github.com/ggml-org/llama.cpp/issues/25618) documents reported greedy differences between speculative and ordinary quantized inference. It includes different operator paths as a contributor. This supports keeping rollback and batch-path equivalence as explicit future gates: our bit-identical 65-frame single-token checks do not cover those mechanisms. It does not establish a new bug in the isolated candidates.
