# Current-server fusion triage

The earlier SwiGLU-to-Q8 fusion was qualified on a different, older stack and reached C1/C2 model checks; its under-load timing did not establish a gain. A read-only review of the reconstructed current server's Vulkan host code finds that the default AMD `ggml_vk_should_use_mmvq` decision returns true for `n > 1` (and permits Q6_K at `n >= 3`). Thus a five-column consumer can meet **this one condition** for Q8 activation quantization. Actual eligibility also depends on integer-dot support, activation type, contiguity, precision, shape and graph ownership. It does not prove that the fusion runs, that its old C1/C2 implementation supports five columns, or that it is faster. A safe port needs graph tracing of the actual producer/consumer shapes and all consumers, followed by exact output checks before timing.

The existing intrusive current-server profile also reports 1,212 GLU calls totaling 2.97 ms, 912 GATED_DELTA_NET calls totaling 34.12 ms, and 4,678 CPY calls totaling 45.40 ms in one aggregate profile. Those entries are not clean per-token latency or a bandwidth measurement: instrumentation changes execution, shapes and contexts are mixed, and some operations or dispatches may overlap. They nevertheless suggest prioritizing attribution of copies and recurrent-state traffic alongside the smaller fusion, instead of assuming the GLU dispatch alone dominates. First identify tensor types, source/destination devices, sizes, dependencies and whether copies are mandatory; preserve synchronization, recurrence, speculative rollback and outputs. The new 0.9 device-feature path could change copy attribution, so profile the actual repaired build separately.

Evidence: [current workload profile](../archive/isolated/current-server-scope/profile/20261102T102358Z/server.log), [old fusion qualification](PRODUCTION-FUSION.md), [current workload scope](WORKLOAD-SCOPE.md). No kernel improvement or deployment recommendation is established by this triage.

A private instrumented capture on the real target/draft with DFlash width 4 surveyed the first 12 Vulkan graphs. It recorded 335 GLU nodes, each with exactly one direct recorded consumer, all `MUL_MAT` using the GLU as input 1. The capture included two five-column graphs with 5 GLU nodes each and one with 64; all have shape `[17408, 5, 1, 1]`. Other graph widths included 2, 4, 9 and 42. This confirms a graph-level opportunity for the observed workload, not Q8-path selection, weight type, all alias-mediated consumers, bitwise equivalence or speed. The instrumented single request completed with no recorded GPU faults; startup had four optional EBUSY sensor gaps. [Plan](../archive/isolated/current-server-scope/glu-consumer/PLAN.md), [instrumentation](../archive/isolated/current-server-scope/glu-consumer/instrumentation.cpp.txt), [capture](../archive/isolated/current-server-scope/glu-consumer/20261108T054203Z/00-n4.log).

A second guarded instrumented capture checked the actual matrix-vector path when its input is a direct GLU node. For shape `m=5120, n=5, k=17408`, the trace reports Q8 activation selection for 1,084 Q4_K, 220 Q5_K and 224 Q6_K calls. These counts are observed dispatch-path entries over a short single request, not per-token costs. It also reports Q6_K at widths 1 and 2 taking the non-Q8 path, so a fusion must retain the existing runtime selection and fallback. This supports pursuing a five-column fusion, but does not establish safety, bitwise identity or performance. The instrumented request completed without recorded GPU errors; startup had optional EBUSY telemetry gaps. [Trace](../archive/isolated/current-server-scope/glu-consumer/20261108T054425Z/00-n4.log), [instrumentation](../archive/isolated/current-server-scope/glu-consumer/mmvq-instrumentation.cpp.txt), [result](../archive/isolated/current-server-scope/glu-consumer/20261108T054425Z/00-result.json).

The preserved standalone SwiGLU-to-Q8 shader was tested with 87,040 flattened elements (five columns of 17,408) using 16 workgroups and six synthetic input patterns. Its floating output and packed Q8 bytes matched its standalone two-stage controls in all six cases, buffer guards passed, and no new GPU faults were recorded. This is an older standalone shader/control comparison with a private Mesa driver, not a current-backend integration, current native shader parity, model-output test or speed result. [Checks](../archive/isolated/current-server-scope/glu-five-probe/checks.json), [log](../archive/isolated/current-server-scope/glu-five-probe/probe.log), [harness](../archive/isolated/current-server-scope/glu-five-probe/probe.cpp).

In the first 12-graph capture, 27 of 74 five-column GLU-to-matmul pairs were adjacent in graph order and 47 had exactly one intervening node. This is graph structure only: the earlier log did not record the intervening node's operation or dependencies, so it does not prove those pairs can safely be fused. A strict adjacency-only prototype would miss those 47 observed pairs; an expanded guard requires inspecting the intervening operations and alias/dependency safety first.

A follow-up guarded trace found that each of the 47 intervening nodes in the five-column pairs was a `VIEW`; all 235 intervening nodes across the captured shapes were `VIEW` nodes. A `VIEW` being metadata-only does not itself establish alias safety or that deferring its producer is valid: its consumers, lifetime, output aliases and synchronization must still be checked. The request completed without recorded new GPU errors; startup had optional EBUSY sensor gaps. [Trace](../archive/isolated/current-server-scope/glu-consumer/20261108T054838Z/00-n4.log), [instrumentation](../archive/isolated/current-server-scope/glu-consumer/between-instrumentation.cpp.txt).

An initial private [port generator](../archive/isolated/current-server-scope/glu-fusion-port/make_draft.py) creates draft backend files from pinned current and older reference sources. It limits the fusion to adjacent five-column cases and retains the Q8 selection check, with Q6_K included because the current trace observed it. The draft has not been reviewed for all source-version differences, compiled, executed, checked for alias and scheduling correctness, or benchmarked. It is not deployable; the VIEW-separated cases remain outside its guard.

The private adjacent-only five-column backend prototype now compiles. A Vulkan-selected operator harness compared fusion disabled versus enabled across four synthetic patterns, four GLUs and Q3_K/Q4_K/Q5_K/Q6_K downstream matrices. All 5,574,400 captured bytes matched; 3,224 fusion calls were logged across warmups and checks, with no recorded new GPU faults. This is a small synthetic operator test using the same candidate backend in both modes, not model or performance qualification; Q3_K is the first consumer, so it does not prove that Q4_K, Q5_K or Q6_K individually trigger fusion. An earlier attempt selected HIP despite the Vulkan library being mapped, had zero fusion calls and is invalid; the corrected harness checks the selected device name explicitly. [Results](../archive/isolated/current-server-scope/glu-fusion-port/operator-checks.json), [harness](../archive/isolated/current-server-scope/glu-fusion-port/operator.cpp), [runner](../archive/isolated/run_current_glu_fusion_operator.py).

The synthetic operator audit was extended to four first-consumer orders. Separate logs show that Q3_K, Q4_K, Q5_K and Q6_K each actually triggered the five-column fusion, and each enabled arm matched its own disabled arm over 5,574,400 captured bytes across four patterns. No new GPU errors were recorded. This remains a small synthetic test; it does not cover all shapes, aliasing, real model outputs or speed.
