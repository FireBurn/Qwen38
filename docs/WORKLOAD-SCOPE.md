# Workload scope and next benchmark

The completed wide and hierarchical argmax measurements use a frozen aa8/0.7 stack, one-token MTP speculation, greedy temperature-zero sampling, a 4,096-token context limit and a short Roman-history prompt. They are controlled local measurements, not measurements of every configuration on the machine. The hierarchical experiment used a private one-dword-copy RADV override; the independently confirmed wide configuration used a separate private two-dword-copy setup.

A `llama server` process observed on 31 October 2026, which was stopped at the user's request before the private benchmark, used a Q3LynnStyle target with a DFlash2 Q4_K_M draft, `ngram-mod,draft-dflash`, four maximum draft tokens, a 327,680 context limit, q8 KV, Flash Attention, temperature 0.6, top-k 20, top-p 0.95, and min-p 0. The command is an observed historical configuration, not proof of the user's currently preferred workload or typical populated context. It uses a different speculation and sampling chain from the argmax tests. Backend sampling was enabled in that command, but the restricted greedy argmax path is not qualified for the full non-greedy chain. No speed result from these experiments should be attributed to that server configuration without measuring it directly.

On 1 November, the installed command reported llama.cpp `0.8.0-dev` build 12033, commit `785322d17`; this differs from the frozen `aa8ab0504` test stack. Installed target and draft model files exist, but equal filenames or equal byte sizes do not establish identical content to the earlier benchmark model. No installed files or user workspace were changed by this review.

The next actionable baseline should reproduce the observed target/draft, sampler and installed stack in an isolated process with the server stopped or otherwise no GPU competition. Use matched workloads at several *populated* context lengths, record output correctness or distributional acceptance appropriate to stochastic decoding, draft acceptance, token speed, context and memory residency; a 327,680 context allocation does not mean every request contains that many tokens. Measure changes as paired stock-versus-candidate runs on the same stack and load, and avoid assuming that gains from the frozen greedy workload transfer. The prior fault and private GPU hold remain relevant; use qualified bounded diagnostic steps and stop on a new fault.

Prior DFlash benchmark JSON in the separate worktree uses a different Q4 target and varying settings; its reported rates are historical leads, not a direct comparison with the observed Q3 server or a basis for claiming an improvement. Preserve the user's original production settings unless a separately validated change is adopted.

## Initial current-server smoke run

One isolated installed-server run completed a short synthetic request at the observed context allocation and DFlash settings with no new GPU errors. Device-wide observed VRAM peaked at about 29.46 GiB, which is not isolated per-process accounting; the prompt was short despite the large allocation. Two telemetry reads returned `EBUSY` without phase tags, so the runner failed its telemetry gate and the timing is **not qualified**. The `passed` field in the raw result means the HTTP request completed; [qualification](../archive/isolated/current-server-scope/baseline/20261101T202654Z/qualification.json) records the failed gate. This was not an A/B test or a quality check. The server log also reported that `cache_reuse` was disabled for this context; this does not establish that ordinary prefix caching is disabled. A separate [width-3 versus width-4 plan](../archive/isolated/current-server-scope/DFLASH-WIDTH-PLAN.md) is prepared with phase-tagged telemetry, matched load and a separate quality gate. The one-dword copy override and disabled transfer queue were explicitly applied to this private process and were not confirmed as the settings of the historical server.

## DFlash width discovery

The fixed24 comparison of DFlash maximum width 3 versus the observed width 4 completed on the installed stack. All requests returned 512 tokens and the same response hash for this one prompt and seed; no new GPU errors were recorded, and pinned libraries/model file identities remained unchanged. Background CPU/build load changed substantially: only two of six blocks met the predeclared matching criteria, below the minimum of four. The comparison is **inconclusive** and did not trigger confirmation. The all-block estimate, which includes unmatched load, was −3.35% for width 3 with a descriptive interval from −16.00% to +11.22%; it is not evidence for a configuration change. One seed/prompt does not establish stochastic output equivalence or long-context behavior. [Analysis](../archive/isolated/current-server-scope/dflash-width/20261102T101450Z/analysis.json), [verification](../archive/isolated/current-server-scope/dflash-width/20261102T101450Z/postrun-verification.json).

## Research leads

- [GPU-resident speculative decoding for WebGPU](https://arxiv.org/abs/2610.39761) explores keeping draft, verification, acceptance and KV maintenance on device, alongside adaptive speculation. Its reported results use browser runtimes, small models and greedy decoding; they do not establish an R9700/Vulkan/DFlash speedup. The local question is whether CPU/GPU synchronization and speculative control are exposed on the actual configuration, and whether exact stochastic sampling and rollback can be preserved.
- [SpecStream](https://arxiv.org/abs/2609.33184) studies streaming committed KV chunks and overlapping target verification with drafting in an offload setting. It motivates measuring populated long-context KV traffic and safe target/draft overlap, not assuming CPU offload is beneficial on this single GPU. Rollback, synchronization, bandwidth contention and resident-memory behavior need local measurement.

## Intrusive operator profile

A single instrumented installed-server run completed its 16-token warmup and 32-token synthetic request with no new GPU errors. Vulkan's performance logger emitted two aggregate tables; they combine initialization, prompt processing, draft and target work, and timestamp instrumentation changes execution. They do **not** measure normal decode throughput or justify adding their totals as latency shares. Three optional startup sensor reads returned EBUSY.

The tables nevertheless identify actual shapes worth investigating: Q3_K matrix-vector operations at verification widths 4 and 5; Q3_K matrix operations at prompt widths 9, 25 and 42; vocabulary TOP_K at K=20 over 248,320 entries; copies; and GATED_DELTA_NET. Flash attention also appeared at these short populated contexts. The largest listed Q3_K width-5 row accounted for 780 instrumented calls, while the K=20 top-k row had 59; these counts are aggregate observations, not isolated per-token costs. The stochastic K=20 sampling path is a more relevant investigation for this server than the previously measured greedy argmax, but any replacement must preserve ordering, ties, NaNs and sampling semantics and demonstrate an end-to-end benefit with matched current-stack tests. [Raw profile and identity](../archive/isolated/current-server-scope/profile/20261102T102358Z/).

The upstream revision reported by the installed server uses a multi-pass top-k for K=20, reducing each workgroup chunk to K repeatedly. Depending on device capabilities, the shader uses N-ary threshold selection or bitonic sort; the actual selected pipeline has not yet been independently confirmed. Larger chunks might reduce intermediate work and dispatches, but may also cost more per workgroup. Tie/NaN ordering, sampler behavior and vector lengths require qualification. This is a hypothesis, not a measured improvement. The exact upstream commit and 25 package patches were reconstructed privately from the installed package metadata and the recorded overlay commit. All applied using patch; five required fuzz, so this is not proof of an identical build. [Reconstruction record](../archive/isolated/current-server-scope/installed-source-reconstruction.json).

On 2 November, SHA-256-identical historical logits were consolidated using atomic hardlinks, reclaiming 9,993,843,240 bytes while retaining all paths. These hardlinked paths must be treated as immutable: writing through one changes the others. [Cleanup record](../archive/isolated/historical-logits-dedup-20261102.json).

## DFlash2 anchor selector lead

The installed draft GGUF reports DFlash2 selector top-k 16 and rank 256. In reconstructed source, the selector computes candidate and gate data for the anchor even though lattice scoring starts at the following position. A private source candidate removes that anchor work only for a single sequence while retaining full logits and the multi-sequence path. A 512-case CPU index-mapping audit passes, but it does not test floating-point behavior, tensor safety, model output, or speed. Changing matrix width could change rounding. [Candidate and qualification plan](../archive/isolated/current-server-scope/dflash-selector-anchor/PLAN.md).

The private baseline and anchor-selector candidate libraries both compiled successfully in the same build tree. This establishes buildability only; no model execution has yet qualified either library, and compatibility with the installed server remains untested. [Build hashes](../archive/isolated/current-server-scope/dflash-selector-anchor/build-summary.json).

An initial instrumented current-server check compared the same private rebuilt baseline and anchor-selector candidate at DFlash width 4. All 12 captured lattices (each five rows of 5,120 floats) matched byte-for-byte; both seeded response hashes and acceptance counts also matched, with no new GPU errors. The baseline recorded three optional sensor EBUSY gaps. The two short requests cover one seed and single-sequence, short populated contexts only; the capture hook perturbs execution and these timings are not an A/B speed result. Multi-sequence, additional widths and contexts, sampler behavior, and independent timing remain to be checked. Raw lattice captures remain local; [comparison, identities and logs](../archive/isolated/current-server-scope/dflash-selector-anchor/lattice-check/20261107T143819Z/).

A broader instrumented single-sequence check also passed: width 3 on a 905-token synthetic technical/math prompt produced 47 identical lattices, and width 4 on a 79-token coding prompt produced 48 identical lattices. Each requested 128 generated tokens, with matching seeded response hashes and draft/accept counts; no new GPU errors occurred. This extends the evidence but covers just two prompts at one seed, not multi-sequence, very long context or a performance comparison. [Results and protocol](../archive/isolated/current-server-scope/dflash-selector-anchor/broad-lattice-check/20261107T144025Z/).

A two-slot concurrent-request run produced matching response hashes, counters and multisets of 103 lattice records per arm, with no new GPU errors. However, its graph trace logged two-sequence graphs only before the server began listening; after listening, the logged selector graphs were single-sequence. The original comparison marked the run passed because it counted startup graph construction. That field **does not qualify multi-sequence execution**; the separate [qualification](../archive/isolated/current-server-scope/dflash-selector-anchor/multiseq-check/20261107T144413Z/qualification.json) supersedes that interpretation. Graph construction alone does not prove graph execution.

A separate DFlash-only two-slot diagnostic logged successful process calls with two active sequences, but post-listening graph traces still showed single-sequence selector graphs; internal splitting is possible. Baseline and candidate produced different lattice multisets and seeded concurrent responses, so that comparison failed its exact-output gate. A subsequent, separately planned baseline-versus-baseline control also produced different lattice multisets and responses under the same concurrent setup; its two sets of response hashes matched the two patterns seen in the failed comparison. Therefore the difference cannot be attributed to the candidate from this evidence, and multi-sequence graph execution remains unqualified. No new GPU errors were recorded. [Comparison](../archive/isolated/current-server-scope/dflash-selector-anchor/multiexec-check/20261107T144709Z/comparison.json), [baseline repeatability control](../archive/isolated/current-server-scope/dflash-selector-anchor/multirepeat-check/20261107T144814Z/comparison.json).

## Two-sequence draft batching lead

The draft GGUF reports non-causal attention. In the reconstructed source, non-causal decode sets `embd_all`, and the non-unified KV-cache path uses `split_seq` in that case. This is consistent with the two-slot trace: successful DFlash process calls contained two active sequences, but selector construction during requests used one sequence per graph. In the baseline repeatability control, the second request joined before the first draft in one run and after it in the other; this scheduling difference correlates with different responses but does not establish the cause.

A separate private candidate narrowly tries to combine two complete five-token DFlash2 sequences into one ubatch. It compiled, but has not been run or qualified; attention isolation, cache behavior, numerical output and performance all remain open. It can only affect concurrent sequences, not single-sequence inference. [Candidate and plan](../archive/isolated/current-server-scope/dflash-two-seq/PLAN.md).

The two-sequence guard passed 50,000 CPU cases against a structural oracle. Source review found sequence membership checks in the attention-mask path and batch-index restoration for unmasked nextn outputs, but neither demonstrates actual attention isolation, cache correctness or numerical equivalence. A controlled per-sequence perturbation remains required before GPU timing. [Review and guard audit](../archive/isolated/current-server-scope/dflash-two-seq/SOURCE-REVIEW.md).

The fixed-input empty-draft-KV isolation probe passed for the baseline: each sequence stayed bit-identical when the other anchor changed, and repeated inputs matched. Candidate and baseline lattice captures were also identical, but the candidate did not produce the required two-sequence graph trace, so the test exercised its fallback and is **inconclusive** for the proposed batching. No new GPU errors were recorded. [Qualification](../archive/isolated/current-server-scope/dflash-two-seq/isolation/20261107T145610Z/qualification.json).

**Correction:** the current DFlash draft constructs `llama_kv_cache_iswa`, whose own `init_batch` performs the non-causal sequence split. The first two-sequence candidate modified `llama_kv_cache::init_batch`, a different path; its guard was never reached in four successful probe cases. The earlier description of the split identified the generic mechanism but did not identify the actual class used by this model. The candidate is ineffective for this workload; its equal capture only tests the unchanged fallback. No new GPU errors were recorded. [Diagnostic qualification](../archive/isolated/current-server-scope/dflash-two-seq/guard-diagnostic/20261107T145753Z/qualification.json).

The revised candidate targeted `llama_kv_cache_iswa` and the probe log showed its guard hit and a two-sequence, ten-token selector graph. The captured candidate lattices repeated exactly and preserved the other sequence under anchor perturbations, but differed from the baseline, including different selected token IDs. The run also failed its library-mapping gate because the candidate process exited before the monitor captured its maps; the output difference cannot be conclusively attributed from this run. The candidate is **not qualified** and was not timed. No new GPU errors were recorded. The diagnostic used synthetic token blocks with an empty draft KV. [Qualification and logs](../archive/isolated/current-server-scope/dflash-two-seq/iswa-isolation/20261107T150037Z/qualification.json).

A separately instrumented fixed-input diagnostic verified private baseline/candidate libllama and RADV mappings inside each process and reproduced the merged-versus-split lattice difference with no new GPU errors. Input embeddings and first-layer normalization were bit-identical. The earliest observed difference was the first layer’s input-side dynamic convolution (50,890 of 51,200 floats differed; maximum absolute difference about 0.0704); subsequent captured operations differed more. The callback synchronizes execution, the input was synthetic with empty draft KV, and this identifies an observation point rather than the root cause. It does not qualify the candidate or measure speed. [First-layer analysis](../archive/isolated/current-server-scope/dflash-two-seq/node-detail-diagnostic/20261107T150554Z/node-analysis.json).

Further mapped, instrumented captures located the first observed difference at the first-layer Q4_K dynamic projection: all 12,800 captured values differed (maximum absolute difference about 0.109), while the convolution input values matched exactly. The source selects a matrix-vector path at up to eight columns; this comparison changes from two five-column calls to one ten-column call, so a different matrix path is a plausible cause. In a separate diagnostic candidate, forcing that projection to remain as two five-column operations restored bit-identical first-layer projection, tap weights, tap products and convolution output. The final lattice still differed, showing that this did not restore full graph equivalence. Neither instrumented run establishes performance or general correctness. [Original projection analysis](../archive/isolated/current-server-scope/dflash-two-seq/conv-nodes/diagnostic/20261107T150842Z/analysis.json), [split-projection analysis](../archive/isolated/current-server-scope/dflash-two-seq/conv-nodes/split-projection-diagnostic/20261107T151031Z/analysis.json).

Further fixed-input diagnostics preserved the original five-column dynamic and Q/K/V projections inside the merged graph. The first-layer input, convolution and Q/K/V then matched bit-for-bit, while the pre-output-projection attention result still differed (40,958 of 40,960 float values; maximum absolute difference about 0.0231). This narrows the observed mismatch to attention or its cache/mask inputs, without identifying a root cause. The final lattice remained different. No new GPU errors occurred; callback captures are intrusive and cannot qualify model speed or general numerical behavior. [Attention analysis](../archive/isolated/current-server-scope/dflash-two-seq/conv-nodes/attention-diagnostic/20261107T151414Z/node-analysis.json).

A no-Flash-Attention Q8 V control could not create a context because this build requires FA for a quantized value cache. Two separate controls used Q8 K and F16 V instead: after matching Q/K/V, split and merged pre-projection attention outputs were bit-identical with FA disabled, but differed with FA enabled (40,953 of 40,960 floats; maximum absolute difference about 0.02491). Later tensors and lattices differed in both controls. This associates the first attention-output difference with the FA-enabled path for this single intrusive synthetic input and cache configuration; it does not establish whether the cause is accumulation, masks, cache layout or a shader issue, or justify changing FA settings. No new GPU errors were recorded. [No-FA analysis](../archive/isolated/current-server-scope/dflash-two-seq/conv-nodes/attention-no-fa-f16v-diagnostic/20261107T151641Z/node-analysis.json), [FA analysis](../archive/isolated/current-server-scope/dflash-two-seq/conv-nodes/attention-fa-f16v-diagnostic/20261107T151721Z/node-analysis.json).

A private FA host trace explained a configuration change in the fixed F16-V probe: the split baseline used multi-query folding of five rows and four KV splits, while the merged graph used no folding and one split. With folding disabled for both, the baseline used two splits and attention outputs still differed. With folding disabled and a diagnostic override forcing one split in both, the captured pre-projection attention output matched bit-for-bit. The final lattices remained different. This identifies split choice as the immediate source of the observed attention discrepancy in this one instrumented probe, not a general FA bug or recommendation to disable splitting; no performance was measured. [Dispatch comparison](../archive/isolated/current-server-scope/dflash-two-seq/fa-trace/dispatch-analysis.json).

With Q/K/V and FA output made bit-identical by the diagnostic controls, the next difference appeared immediately after the Q4_K attention output projection: all 51,200 captured values differed, maximum absolute difference about 34.57 in the synthetic empty-KV probe. This is another five-versus-ten-column projection and is a strong lead, not proof of a specific shader defect. Preserving split-style numerical behavior by splitting every changed projection may reduce the potential batching benefit; it has not been benchmarked. No new GPU errors occurred.
