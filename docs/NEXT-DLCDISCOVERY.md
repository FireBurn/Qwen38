# Next DFlash workload comparison

The next candidate is a **configuration experiment**, not a claim that a kernel is faster: compare DFlash maximum draft width 5 with the observed width 4. Wider verification could amortize target-weight reads over more proposed tokens, but additional drafting and rejected tokens could outweigh that benefit. Width 3 versus 4 was inconclusive under changing background load; it does not establish what width 5 will do. The existing SwiGLU-to-Q8 fusion had a focused gain on an older stack, but has not established a current-server model gain. Its eligibility and integration need to be checked on the active build before extrapolating those results.

Before measuring, identify and freeze the installed executable and all mapped libraries, models and driver. A system llama.cpp 0.9.0 build was in progress when this plan was written, so an experiment must not span its installation. Check that its model and DFlash configuration still work and that relevant options and semantics are unchanged; if not, report the differences and revise the protocol before timing. Keep the target and draft resident, the same context allocation, sampling, Flash Attention and private copy-path overrides as in the earlier server study, subject to compatibility. These overrides were not confirmed for the historical server.

Use a fixed sequence of six alternating ABBA/BAAB blocks, with two fresh processes per width per block, a warmup and one 512-token request each, one short prompt and one seed. Predeclare the exact runner and primary metric before starting. Monitor the CPU, build activity and runnable threads during each request; apply the existing width-study matching thresholds and require at least four matched blocks for a discovery result. Stop on new GPU faults, competing GPU work, unexpected process failures, changed pinned files, or missing mandatory telemetry. Do not silently retry or pool additional runs. Report all blocks, matching, confidence interval, output hashes and draft/accept counts. Different speculative widths can change seeded outputs; a speed gain alone is not a correctness or quality demonstration.

A positive lower descriptive interval is a discovery signal only. Independently confirm it with fresh data and evaluate correctness, sampled output distributions, multiple prompts and populated longer contexts before recommending a change. If the gain is absent, consider the result workload-specific and continue investigating current-stack kernel bottlenecks rather than combining unproven improvements on the assumption that they add together.

A read-only comparison of the in-progress 0.9.0 package source with the reconstructed 0.8.0-dev source found a new DFlash target-feature device-buffer path. In the 0.9.0 source it is eligible when the extract-layer IDs are strictly ascending, the draft backend supports embedding rows, the model is not LiLiCorr, and `LLAMA_DFLASH_DEV` is unset or nonzero; it falls back to host copies otherwise. The prepared runner clears `LLAMA_` environment variables, so this feature would be enabled by default if its runtime checks pass. This is source inspection, not proof that the built server uses the device path or that it is faster. Capture the runtime path marker and library identities after installation; width results on the new path cannot be treated as a direct continuation of old-version results. A separate on/off A/B may be useful if both paths work, but requires its own fixed protocol and correctness checks.

The prepared runner records the feature-path log marker for every process and rejects a change between arms. It records `unreported` when no recognized marker appears; that does not establish which path was used. A syntax check and CPU-only preflight passed, but the updated runner has not been exercised against a running 0.9.0 server.

A separate [frozen-stack runner](../archive/isolated/run_current_dflash_width_frozen.py) and [protocol](../archive/isolated/current-server-scope/DFLASH-WIDTH-FROZEN-PLAN.md) allow the comparison to proceed during the ongoing installation. The unrelated system 0.9.0 emerge completed during the frozen-stack run. Afterwards `/usr/bin/llama-server --version` failed at dynamic linking: the installed Vulkan library has unresolved `concat_transpose_i32_len` and `concat_transpose_i32_data` symbols. This is an observed installation failure, not a benchmark result or an attributed cause. The private frozen 0.8.0 executable still prints its version with its private library path, and the ongoing comparison uses that snapshot. The system package needs repair or replacement before the installed server can be used; the private test did not modify it.

The installed-library link failure has a concrete source explanation: the overlay’s `0015-vulkan-concat-with-a-transposed-src1-through-shared-.patch` adds generator and host references to `concat_transpose.comp` but its actual diff omits that new file, despite the patch summary saying it creates it. The 0.9.0 distribution tarball also lacks the file, and the build log has no compilation entry for it. A 61-line shader with identical SHA-256 in the preserved reconstructed source and Claude’s source was used to create a private [missing-file patch](../archive/isolated/llama-090-vulkan-fix/missing-shader.patch); it passes a patch dry run. This candidate has not been rebuilt or runtime-tested for 0.9.0 and has not been applied to the overlay. A proper rebuild should also require the shared-library link to reject unresolved shader symbols.

The frozen 0.8.0 width 5 versus width 4 study completed all 24 requests with no recorded new GPU errors. All response hashes matched on this single prompt and seed; draft/accepted counts were 642/350 at width 4 and 743/362 at width 5. Only one of six blocks passed the predeclared CPU/build/runqueue matching criteria, below the required four, because background activity changed greatly. The all-block geometric estimate was +5.66% (descriptive interval +1.96% to +9.50%), but includes unmatched load and **is not a valid basis for a speed claim**; the study did not qualify for confirmation. The completion of the build suggests a separate quiet-load experiment may be more informative; no data should be pooled with this study. A CPU-only repair diagnostic compiled the missing shader with `glslc` against the preserved 0.8 source headers and passed `spirv-val` for Vulkan 1.2. Separately, a private shared library built from the preserved generated shader source supplied the two missing symbols through `LD_PRELOAD`; with it, the installed 0.9.0 `llama-server --version` printed successfully. Without the preload it still fails. This supports the missing-symbol diagnosis, but neither check exercises the 0.9 model, shader execution or numerical correctness. The preload is a diagnostic, not a tested deployment fix; the overlay patch and proper rebuild remain necessary.
